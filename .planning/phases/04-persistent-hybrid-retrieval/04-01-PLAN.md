# Phase 4 Plan 04-01: Persistent LanceDB Vector Store & CPU-Pinned Embedding Pipeline

## Goal

Establish the persistent LanceDB storage backend (`hybrid_retriever.py`) and enforce CPU-pinned Sentence-Transformers (`all-MiniLM-L6-v2`) embeddings, replacing ephemeral in-memory vector storage with an on-disk embedded store (`data/lancedb/`) that survives process restarts while guaranteeing zero GPU VRAM consumption (RETR-01, RETR-02).

## Requirements covered

- **RETR-01**: System generates dense text embeddings using local Sentence-Transformers (`all-MiniLM-L6-v2`) pinned to CPU to protect the 4 GB GPU VRAM.
- **RETR-02**: System indexes document chunks and embeddings into a persistent on-disk LanceDB table that survives application restarts.

## Depends-on

- Phase 1 canonical models (`models.py`, `Chunk`, `Document`).
- Phase 3 multimodal chunks and metadata persistence in SQLite (`doc_store.py`).

## Tracer Slice

Construct `HybridRetriever(db_uri=tmp_path / "lancedb")` → embed sample chunks using CPU-pinned `LocalEmbedding` → insert vectors and metadata into LanceDB `chunks` table → close and re-open retriever instance → execute nearest-neighbor vector search → verify chunks and cosine scores persist identically across reload → verify fallback to in-memory `VectorIndex` when LanceDB is unavailable.

## Codebase Map Alignment

- **ARCHITECTURE.md**: Replaces the in-memory `VectorIndex` linear scan in the retrieval layer with persistent LanceDB embedded tables. Maintains strict one-way dependency flow into canonical `models.py`.
- **CONCERNS.md**:
  - Direct mitigation of **"Vector index is in-memory only"**: LanceDB persists vectors and chunk metadata on disk in `data/lancedb/`.
  - Direct mitigation of **"Working-directory-relative artifact paths"**: Default storage path is anchored to `Path(__file__).resolve().parent / "data" / "lancedb"`.
  - Direct mitigation of **"Unpinned heavy dependencies"**: Adds `lancedb>=0.17.0` and `pyarrow>=14.0.0` to `requirements.txt`.
- **CONVENTIONS.md**:
  - Implements flat module structure at repository root (`hybrid_retriever.py`).
  - Follows mandatory optional-dependency pattern (`try: import lancedb ... except ImportError: lancedb = None`) with graceful degradation.
  - Replaces raw `print()` statements with standard `logging.getLogger(__name__)`.
- **INTEGRATIONS.md**: Embeddings pinned strictly to CPU (`device="cpu"`) to protect the 4 GB GPU VRAM for the local VLM (`llama-server`).
- **STACK.md**: Declares `lancedb` and `pyarrow` in `requirements.txt`.
- **STRUCTURE.md**: Places `hybrid_retriever.py` in repo root and tests in `tests/test_hybrid_retriever.py`.
- **TESTING.md**: Verifies persistent store, CPU device pin, and fallback mode with 100% offline unit tests.

## Design Locks

- **D1 Explicit CPU device pinning:** `LocalEmbedding.__init__` must explicitly pass `device="cpu"` to `SentenceTransformer(self.model_name, device="cpu")`, ensuring PyTorch never creates a CUDA context or allocates VRAM from the 4 GB GPU budget.
- **D2 Anchored persistent storage path:** Default LanceDB storage URI must be anchored to repository root (`Path(__file__).resolve().parent / "data" / "lancedb"`), preventing process working-directory drift.
- **D3 Optional-dependency fallback:** If `lancedb` is not installed or unavailable in the environment, `HybridRetriever` logs a warning and gracefully delegates to `VectorIndex` in-memory store, preserving 100% backward compatibility and test stability.
- **D4 Canonical chunk schema:** The LanceDB `chunks` table stores `chunk_id`, `doc_id`, `filename`, `page`, `content`, `vector` (384 float32), `extraction`, `char_start`, `char_end`, and `bbox_json`.
- **D5 Deduplication on write:** Insert operations deduplicate by `chunk_id`, allowing idempotent re-indexing.
- **D6 Document deletion lifecycle:** Provides `delete_document(doc_id: str)` to clean up LanceDB rows when documents are removed.
